# 商业版双模式路线图与第一阶段范围

更新时间：2026-07-08

## 结论

EyeTimeTracker 后续主线调整为：先把中文版商业版做扎实，再考虑海外英文版和配套网站。

商业版不是另做一个独立儿童 App，也不是从零开始。它应从已经完成的 PC 与 Android 用眼统计、提醒、多端同步能力继续演进，在同一个“用眼健康 App”里形成个人护眼模式和家庭护眼模式。家庭护眼模式包含孩子 App 使用统计、App 限制和家长规则，但它是现有产品的扩展，不是新的独立产品线。

当前不立刻开发鸿蒙版和 iOS 版，但从第一阶段开始就要把账号、家庭、规则、设备、支付和数据模型设计成可扩展，避免以后为鸿蒙、iOS 或云同步重做流程。

## 产品定位

商业版面向成人个人用户和家庭用户。成人关注自己的用眼健康，也有付费价值；家长通常对孩子用屏管理更愿意付费，因此家庭护眼模式是商业化重点，但不能因此把个人护眼模式丢掉。

个人护眼模式解决的问题是：

- 用户知道自己每天手机和电脑总共用了多久。
- 用户知道自己什么时候连续用眼最明显。
- 用户能收到休息提醒。
- 用户能看到趋势和护眼表现。

家庭护眼模式解决的问题是：

- 家长知道孩子每天用了多久手机或平板。
- 家长知道孩子主要把时间花在哪些 App 上。
- 家长可以设置规则，例如每日总时长、某类 App 时长、睡前禁用、学习时间保护。
- 孩子可以看到剩余可用时间和休息提示，减少突然被锁定带来的对抗感。
- 家长可以在合理范围内远程调整规则、查看报告、管理会员。

健康建议仍然只做生活方式建议，不做医学诊断，也不承诺治疗近视或眼病。

## 平台策略

### Android 手机和平板

第一优先级。Android 是商业版完整能力验证平台，既承接个人护眼模式，也优先完成家庭护眼模式。

计划能力：

- 统计总屏幕使用时间。
- 统计具体 App 使用时长。
- 设置具体 App 或 App 类别的使用限制。
- 到达限制后显示限制页面或休息提示。
- 支持家长密码、规则修改保护和权限关闭提醒。
- 适配手机和平板布局。

### 鸿蒙

纳入路线图，但不作为第一阶段开发对象。

原因：

- 中国家庭场景中华为手机和平板占比不低，尤其儿童平板和家长机都可能出现鸿蒙设备。
- 鸿蒙 NEXT 走原生生态后，不能长期假设 Android APK 能覆盖所有华为设备。
- 儿童控制类功能高度依赖系统权限，必须单独验证鸿蒙是否允许读取 App 使用、判断当前 App、弹出限制页面和稳定后台运行。

计划在 Android 儿童版核心流程跑通后，做鸿蒙可行性验证。如果权限足够，再排入正式适配；如果权限不足，则做统计、提醒、报告为主的降级版。

### iOS 和 iPadOS

纳入路线图，但按降级能力规划。

Apple 平台对屏幕时间、家长控制、系统限制能力有较强边界，不能按 Android 的能力承诺。iOS/iPadOS 版本应先验证系统允许的能力，再决定能做到：

- 统计和提醒；
- 家长报告；
- 与家庭账号同步；
- 有限规则管理；
- 或通过 Apple 允许的专门能力做更深控制。

不能把 Android 的“限制具体 App”直接承诺到 iOS。

### Windows PC

不做孩子设备限制的主平台。

Windows 版继续作为个人护眼和跨设备统计伴侣存在，适合成人用户或家长了解电脑屏幕使用情况。家庭护眼模式中的孩子设备限制重点放在手机和平板。

## 总体路线图

### 阶段 0：方向确认与产品边界

目标是把产品主线改为中文版商业版优先，并明确同一个 App 内包含个人护眼模式和家庭护眼模式。

产出：

- 明确 Android 手机和平板是第一完整平台。
- 明确 Windows 不做儿童控制主平台。
- 明确 iOS/iPadOS 与鸿蒙都要纳入规划，但先做能力验证。
- 明确英文海外版后置。
- 明确家庭护眼模式不是独立 App，而是在现有个人护眼基础上的扩展。

状态：本轮已确认。

### 阶段 1：审核与合规底稿

目标不是写最终上架材料，而是提前建立合规框架，避免后续功能做完才发现权限、数据或儿童隐私说明无法自洽。

这一阶段只做内部底稿，不做最终提交版本。正式隐私政策、数据安全表、商店说明、儿童隐私条款，应等核心功能和第三方服务基本稳定后再定稿。

详细范围见下方“第一阶段范围”。

### 阶段 2：账号、家庭与服务器基础

目标是先把商业化产品的底座搭好。

范围：

- 家长账号注册和登录。
- 家庭空间。
- 孩子档案。
- 设备绑定。
- 规则保存和同步。
- 使用记录上传和查询。
- 数据删除和导出。
- 基础后台管理。

这一步要为后续支付、会员、鸿蒙、iOS 和网页登录留入口。

### 阶段 3：Android 家庭护眼核心能力

目标是在 Android 手机和平板上，在现有个人护眼能力基础上完成家庭护眼最小可用闭环。

范围：

- 读取 App 使用时长。
- 显示孩子今日和本周使用情况。
- 设置每日总时长。
- 设置单个 App 或 App 类别时长。
- 到达限制后显示限制页面或休息页面。
- 家长密码保护设置入口。
- 权限关闭、后台被限制时给出清晰提醒。
- 手机和平板布局适配。

第一版不追求“完全无法绕过”，但要做到普通家庭日常使用可靠。

### 阶段 4：家长和孩子体验完善

目标是降低家长理解成本，也降低孩子抵触感。

范围：

- 家长报告。
- 每日和每周趋势。
- 孩子剩余时间显示。
- 孩子申请延长时间。
- 家长远程批准或拒绝。
- 学习类、娱乐类、社交类 App 分类。
- 睡前用机提醒和夜间规则。
- 护眼建议和休息建议。

### 阶段 5：支付与商业闭环

目标是从可用产品变成可收费产品。

范围：

- 免费版和会员版能力边界。
- 会员购买、续费、取消和恢复。
- 国内支付方案。
- 如果进入 Google Play，则接入 Google Play 的应用内购买。
- 如果进入 Apple 平台，则按 Apple 规则处理会员购买。
- 订单、发票、退款和客服流程。

支付不能最后才做，因为它会影响账号、会员权限、商店审核和用户协议。

### 阶段 6：鸿蒙可行性验证

目标是在正式投入鸿蒙开发前确认系统能力边界。

验证点：

- 是否能读取 App 使用时长。
- 是否能判断当前正在使用的 App。
- 是否能弹出限制页面或强提醒。
- 后台运行是否稳定。
- 家长授权流程是否可接受。
- 华为应用市场是否接受相关权限用途。

验证通过后再决定正式适配范围。

### 阶段 7：iOS/iPadOS 降级版验证

目标是确认 Apple 平台能做到什么，不提前承诺 Android 同等能力。

验证点：

- 可用的屏幕时间或家庭控制能力。
- 是否需要特殊授权或申请。
- 审核和商业化限制。
- 与账号、家庭、支付系统的衔接。

### 阶段 8：内测、上架准备与发布

目标是把产品变成可以给真实家庭使用和付费的版本。

范围：

- 内测家庭招募。
- 崩溃和异常上报。
- 权限引导打磨。
- 隐私政策和用户协议定稿。
- 商店截图、介绍文案和审核材料。
- 客服入口。
- 常见问题说明。
- 数据删除入口验证。

### 阶段 9：海外版和配套网站

目标是在中文版儿童版跑通后，重新启动英文市场。

范围：

- 英文界面实装和逐屏检查。
- 海外官网。
- 海外隐私政策。
- 海外支付。
- 海外应用市场上架。
- 海外内容和客服体系。

## 第一阶段范围

第一阶段名称：审核与合规底稿。

第一阶段目标：提前把儿童控制商业版可能涉及的数据、权限、家长同意、平台差异、审核风险写清楚，但不把任何材料做成最终上架版本。

### 需要产出的文档

1. 数据清单底稿

   写清楚未来可能收集、保存或上传的数据，包括：

   - 家长账号信息。
   - 孩子档案信息。
   - 设备信息。
   - App 使用时长。
   - App 名称和分类。
   - 屏幕使用总时长。
   - 家长设置的规则。
   - 会员状态和订单状态。
   - 异常日志和崩溃信息。

2. 权限说明底稿

   写清楚每个权限为什么需要，是否必须，用户关闭后会影响什么。

   Android 重点权限包括：

   - 查看应用使用情况。
   - 通知。
   - 悬浮窗或覆盖显示。
   - 后台运行。
   - 无障碍服务，如果后续确认需要使用，必须单独论证。

   其中无障碍服务风险较高，不应在没有明确必要性和审核解释前默认纳入核心方案。

3. 家长同意流程底稿

   写清楚：

   - 谁创建家长账号。
   - 谁添加孩子档案。
   - 谁绑定孩子设备。
   - 孩子端如何说明正在被家长管理。
   - 家长如何删除孩子数据。
   - 家长如何解除设备绑定。
   - 家长和孩子共用一台设备时如何处理。

4. 平台能力边界表

   至少包含：

   - Android 手机。
   - Android 平板。
   - 鸿蒙手机。
   - 鸿蒙平板。
   - iPhone。
   - iPad。
   - Windows PC。

   每个平台标注：

   - 可完整支持。
   - 需要验证。
   - 只能降级支持。
   - 不作为儿童控制平台。

5. 审核风险清单

   写清楚当前最大风险：

   - 儿童数据保护。
   - App 使用数据是否属于敏感数据。
   - 限制具体 App 是否会被视为高风险权限用途。
   - 无障碍服务是否会被平台拒绝。
   - 悬浮窗或限制页面是否影响用户体验和审核。
   - 支付是否必须走应用商店自己的购买系统。
   - 国内上架是否需要备案、软著、隐私合规材料。

6. 第一版服务端数据边界

   写清楚第一版服务器最少需要保存什么，尽量避免过度收集。

   建议第一版只保存：

   - 家长账号。
   - 家庭和孩子档案。
   - 设备绑定关系。
   - 使用时长汇总和必要的 App 使用记录。
   - 规则设置。
   - 会员状态。

   不保存通讯录、精确位置、相册、短信、通话记录等与产品目标无关的数据。

7. 上架材料待办清单

   不写最终版本，只列出将来必须准备的内容：

   - 隐私政策。
   - 用户协议。
   - 儿童隐私说明。
   - 会员协议。
   - 退款说明。
   - 权限说明页面。
   - 应用商店截图。
   - 数据删除说明。
   - 客服联系方式。

### 第一阶段不做什么

- 不写最终隐私政策。
- 不填写最终应用商店数据安全表。
- 不实现登录、支付、家长控制功能。
- 不开发鸿蒙版。
- 不开发 iOS 版。
- 不引入真实服务器。
- 不承诺任何平台上的强制限制能力。

### 第一阶段完成标准

第一阶段完成时，应该能回答这些问题：

- 儿童版到底收集哪些数据。
- 哪些数据必须上传，哪些可以只留本机。
- 每个权限为什么需要。
- 家长如何同意、管理和删除孩子数据。
- Android、鸿蒙、iOS、Windows 各自承担什么角色。
- 哪些功能存在审核风险。
- 哪些材料需要等功能稳定后再定稿。

只要这些问题能回答清楚，第一阶段就算完成。它的价值是减少后续返工，而不是提前把所有法律和上架文本写死。

## 关键产品决策

- 儿童控制商业版先做中国市场。
- Android 手机和平板先做完整版本。
- Windows 不做儿童控制主平台。
- 鸿蒙必须规划，但先做验证。
- iOS/iPadOS 按降级能力规划。
- 海外英文版后置。
- 合规材料先做底稿，后期再定稿。
- 不为了看起来强大而过早承诺“完全限制孩子无法绕过”。
- 账号、会员、支付、后台管理等常用能力优先复用成熟模板和开源库，不从零开始写。

## 开发复用原则

商业版后续会涉及登录、会员、支付、后台管理、权限管理、邮件通知、官网和多语言内容。这些能力不属于 EyeTimeTracker 的核心差异点，原则上不从零开始写。

优先复用的现有资源：

- 用户已购买模板：`C:\Users\zhouh\Documents\trae\shipany-template-two`
- 模板内已观察到的可复用能力：登录、权限角色、后台管理、支付、订阅、订单、数据库、多语言、官网内容、文档页、邮件、对象存储和客服入口。
- Java 权限认证候选：Sa-Token、Apache Shiro。

当前初步判断：

- 如果后端和管理后台走 Next.js / TypeScript 路线，应优先评估 ShipAny 模板中已有的 `better-auth`、RBAC、支付和订阅模块。
- 如果后端走 Java / Spring 路线，应优先评估 Sa-Token 或 Shiro，而不是自写登录、权限和会话管理。
- 支付模块也应优先复用模板或成熟 SDK。国内支付、Google Play 应用内购买、Apple 应用内购买需要分别按平台规则接入。

正式开发账号、支付和后台前，需要先做一次“模板与开源库评估”：

1. 检查模板许可证，确认可用于本项目商业化。
2. 明确哪些代码可以直接复用，哪些只能参考设计。
3. 检查模板登录、权限、支付、订阅和后台管理是否满足儿童版需求。
4. 比较 ShipAny 现有技术栈、Sa-Token、Shiro 与未来服务器部署方式的匹配程度。
5. 选定一套主方案，避免同时混用多套登录权限系统。
