# 开发协作守则

更新时间：2026-07-08

这份文档用于记录后续开发 EyeTimeTracker 时必须遵守的协作方式。用户不是职业程序员，开发过程应按“产品经理 + 工程协作”的方式推进：先理解需求和现有项目，再判断改哪里，最后用中文说明改动和验证方式。

## 基本原则

- 先阅读项目结构和现有代码，再动手修改。
- 先判断应该改哪些地方，不凭空新增一套结构。
- 尽量沿用当前项目的技术栈和代码风格。
- 不做大规模重构。
- 不删除已有功能。
- 修改必须聚焦当前需求，不顺手优化无关内容。
- 如果需要添加依赖，必须先说明为什么需要。
- 账号、会员、支付、后台管理等常用能力，优先复用已购买模板和成熟开源库，不从 0 写。

## 可优先评估的复用资源

- 已购买模板：`C:\Users\zhouh\Documents\trae\shipany-template-two`
- 模板中已观察到的能力：登录、权限角色、后台管理、支付、订阅、订单、数据库、多语言、官网内容、文档页、邮件、对象存储和客服入口。
- Java 权限认证候选：Sa-Token、Apache Shiro。

正式进入账号、支付、后台开发前，必须先做模板与开源库评估：

1. 检查模板许可证，确认可用于本项目商业化。
2. 明确哪些代码可以直接复用，哪些只能参考设计。
3. 检查模板登录、权限、支付、订阅和后台管理是否满足儿童版需求。
4. 比较 ShipAny 模板、Sa-Token、Shiro 与未来服务器部署方式的匹配程度。
5. 选定一套主方案，避免同时混用多套登录权限系统。

## 每次开发前的固定步骤

任务：【写你的需求】

要求：

1. 先阅读项目结构和现有代码。
2. 判断应该改哪些地方。
3. 尽量沿用当前项目的技术栈和代码风格。
4. 不要大规模重构。
5. 不要删除已有功能。
6. 如果需要添加依赖，请说明为什么需要。
7. 修改完成后，请自己选择合适的方式检查项目是否能正常运行。
8. 如果检查失败，请区分是代码问题，还是环境、网络、权限问题。
9. 最后用中文告诉用户：
   - 改了什么；
   - 改了哪些文件；
   - 用户应该怎么测试；
   - 有没有风险或后续要处理的事情。

## 验证要求

文档改动：

- 至少执行文档格式检查或 Git 差异检查。
- 不需要构建 PC 版，也不需要安装 Android。

代码改动：

- 根据改动范围选择合适检查方式，例如单元测试、构建、APK 安装、手动验证。
- PC 代码改动后，构建 PC 版并给出可点击程序路径。
- Android 代码改动后，构建 APK 并自动安装到已连接设备。
- 如果检查失败，要说明失败属于代码问题、环境问题、网络问题还是权限问题。

## 输出要求

最终回复必须使用中文，并尽量用非技术用户能理解的话说明：

- 改动目的；
- 改动文件；
- 验证结果；
- 用户下一步怎么测试；
- 已知风险和后续事项。

不要只给命令或路径。给路径时尽量使用可点击链接。
